# 训练性能诊断与单机/多机对比

三类常见问题：

- 为什么 2×8 卡任务的单步耗时和单机 8 卡接近；
- 训练慢是计算、数据读取、网络通信还是平台调度导致的；
- 如何用可复现的方式比较单机与多机训练性能。

结论不能只看日志中的 `time`。至少要同时比较全局 Batch、每轮迭代数、样本吞吐、整轮耗时、`data_time` 和 GPU 利用率。

## 1. 先理解四个指标

| 指标 | 含义 | 常见误区 |
| --- | --- | --- |
| 单步耗时 | 一个训练 iteration 的平均时间 | 多机后不一定明显下降 |
| 样本吞吐 | 每秒完成的全局样本数 | 应作为扩卡效果的核心指标 |
| 每轮迭代数 | 一个 epoch 需要执行多少步 | 全局 Batch 翻倍时通常减半 |
| 整轮耗时 | 完成一个 epoch 的墙钟时间 | 最直接反映任务是否加速 |

计算公式：

```text
全局 Batch = Worker 数 × 每 Worker GPU 数 × samples_per_gpu
样本吞吐 = 全局 Batch ÷ 平均单步耗时
加速比 = 多机样本吞吐 ÷ 单机样本吞吐
扩展效率 = 加速比 ÷ GPU 数量倍数
数据等待占比 = 平均 data_time ÷ 平均单步耗时
```

例如，单机 8 卡与双机 16 卡都设置 `samples_per_gpu=8`：

```text
单机全局 Batch = 1 × 8 × 8 = 64
双机全局 Batch = 2 × 8 × 8 = 128
```

双机中每张 GPU 仍处理 8 个样本，所以单步计算量没有减少，单步耗时接近单机是正常现象。但每一步处理的全局样本翻倍，每轮迭代数约减半，因此整轮训练应接近两倍快。

## 2. 当前两个任务的诊断结论

### 2.1 结果摘要

| 项目 | 单机 8 卡 | 双机 16 卡 |
| --- | ---: | ---: |
| Worker 拓扑 | 1 × 8 GPU | 2 × 8 GPU |
| `samples_per_gpu` | 8 | 8 |
| 全局 Batch | 64 | 128 |
| 平均单步耗时 | 3.681 s | 3.609 s |
| 平均 `data_time` | 0.409 s | 0.182 s |
| 数据等待占比 | 11.10% | 5.04% |
| 迭代数/epoch | 2,649 | 1,325 |
| 估算 epoch 耗时 | 162.5 min | 79.7 min |
| 样本吞吐 | 17.39 samples/s | 35.47 samples/s |
| 平均 GPU 利用率 | 88.32% | 91.08% |

双机相对单机的样本吞吐加速约为 `2.04×`。GPU 数量扩大两倍后，当前观测结果接近线性扩展。

### 2.2 平台侧事实

- 双机任务确实创建了两个 GPU Worker，每个 Worker 使用 8 张 GPU，并被调度到不同 GPU 节点；
- 两个 Worker 分别以 `node_rank=0` 和 `node_rank=1` 进入同一个 16 rank `torchrun` 任务；
- NCCL 初始化正常，没有发现 NCCL 超时、OOM 或降级成单节点执行；
- 任务几乎没有排队，慢速不来自 Kueue 调度等待；
- 双机任务平均 GPU 利用率约 91%，没有出现大面积 GPU 空闲；
- `data_time` 只占单步耗时约 5%，当前主要时间消耗在模型前向、反向和优化器计算，而不是数据读取。

因此，这两个任务没有证据表明是平台未启用多机，或数据加载拖慢了双机训练。用户感知“速度和单机一样”，主要是比较了约 3.6 秒的单步耗时，而不是约 2 倍提升的全局吞吐和约减半的 epoch 耗时。

### 2.3 诊断边界

这组数据来自真实任务的日志和监控抽样，适合解释当前问题，但不是严格的科学 A/B 基准：

- 两个任务使用了不同日期的数据索引目录；
- 单机任务通过业务包装脚本启动，双机任务直接进入训练脚本；
- 任务运行时长和日志采样点数量不同。

要形成可公开的正式基准，必须按第 5 节使用完全相同的代码、数据、镜像、参数和测量区间重新执行。

## 3. 如何判断真正的瓶颈

### 3.1 数据读取瓶颈

典型信号：

- `data_time / time` 长期超过 30%；
- `data_time` P95 明显高于中位数，并周期性出现长尾；
- GPU 利用率呈锯齿状，频繁下降到低位；
- 提高 DataLoader worker 数后吞吐显著改善；
- 同一任务热读明显快于首次读取。

当前案例的双机数据等待占比约 5%，不属于主要数据瓶颈。单机存在少量 `data_time` 长尾，但平均占比约 11%，也不是主要耗时来源。

### 3.2 GPU 计算瓶颈

典型信号：

- GPU 利用率长期超过 80%；
- `data_time` 较低；
- 单步耗时稳定；
- 增加 CPU 或 DataLoader worker 后吞吐没有明显提升。

当前两个任务符合这一特征。优化方向应优先考虑模型计算、混合精度、算子实现、每卡 Batch 和编译优化，而不是盲目增加数据加载进程。

### 3.3 跨节点通信瓶颈

典型信号：

- 双机单步耗时显著高于单机；
- NCCL AllReduce 时间占比高；
- 节点间网络持续接近带宽上限；
- 不同 rank 的进度不一致；
- 日志出现 NCCL timeout、connection reset 或 rank 退出。

当前双机单步耗时没有上升，网络吞吐也未显示饱和，因此没有跨节点通信成为主要瓶颈的证据。

### 3.4 CPU、内存或 DataLoader 过度配置

当前双机任务每个 Worker 申请 64 CPU、256 GiB 内存，但观测 CPU 使用约 9–10 核，内存约 193–202 GiB。

`workers_per_gpu=8` 在 8 个训练 rank 下会产生约 64 个 DataLoader 子进程。它暂时没有导致 GPU 等待，但会增加：

- 内存占用；
- 小文件并发和元数据压力；
- 进程切换开销；
- 多任务并发时的存储抖动风险。

建议用相同任务对 `workers_per_gpu=4` 和 `8` 做 300–500 步 A/B 测试，再决定默认值。不要只因节点 CPU 数量多就持续增加 DataLoader worker。

### 3.5 算法稳定性

日志中的 `grad_norm: nan`、验证指标 NaN 或 loss 异常属于算法与数值稳定性问题，不等于平台性能问题。应分别检查：

- 学习率是否随全局 Batch 正确调整；
- FP16 loss scale；
- 梯度裁剪；
- warmup；
- 数据异常值；
- Checkpoint 是否与当前配置兼容。

## 4. 全局 Batch 策略必须先确定

扩卡测试有两种不同目的，不能混为一谈。

### 4.1 吞吐扩展测试

保持每卡 Batch 不变：

```text
1×8 GPU:  samples_per_gpu=8，global_batch=64
2×8 GPU:  samples_per_gpu=8，global_batch=128
```

预期：单步耗时接近，样本吞吐接近两倍，每轮迭代数减半。

这种方式能证明平台扩卡和训练吞吐是否正常，但全局 Batch 改变后，学习率、warmup 和收敛特性可能需要同步调整。

### 4.2 固定全局 Batch 测试

保持全局 Batch 为 64：

```text
1×8 GPU:  samples_per_gpu=8，global_batch=64
2×8 GPU:  samples_per_gpu=4，global_batch=64
```

预期：双机单步耗时应下降，但很难达到严格两倍，因为增加了跨节点 AllReduce，而且每张卡上的计算粒度变小。

这种方式适合比较相同优化语义下的训练时间，不适合直接和“每卡 Batch 固定”的结果混用。

## 5. 标准单机/多机验收流程

### 5.1 固定测试条件

两次任务必须使用相同的：

- 源码快照或 Git commit；
- 训练镜像 digest；
- 数据集版本和标注文件；
- 初始 Checkpoint；
- 随机种子；
- 模型配置；
- 混合精度设置；
- DataLoader 参数；
- 输出日志频率。

提交前保存 `git status` 和配置摘要。平台上传的是当前工作目录快照，未提交的本地改动也会进入任务。

### 5.2 执行两类基准

第一组验证吞吐扩展：

```text
1×8 GPU，samples_per_gpu=8
2×8 GPU，samples_per_gpu=8
```

第二组验证固定全局 Batch：

```text
1×8 GPU，samples_per_gpu=8
2×8 GPU，samples_per_gpu=4
```

如需验证数据缓存，再增加缓存关闭与缓存开启的对照组。不要同时修改 GPU 数、Batch、数据路径和 DataLoader worker，否则无法归因。

### 5.3 测量区间

1. 忽略最初 50–100 步预热；
2. 连续记录后续 300–500 步；
3. 至少完成一个 epoch 时，再记录真实 epoch 墙钟时间；
4. 同时记录均值、中位数和 P95，不只取最快一步；
5. 保存任务 ID、时间范围和 MLflow Run。

### 5.4 必须记录的结果

| 分类 | 指标 |
| --- | --- |
| 拓扑 | Worker 数、每 Worker GPU、world size、节点数 |
| 训练 | 全局 Batch、迭代数/epoch、平均/P50/P95 单步耗时、samples/s |
| 数据 | 平均/P50/P95 `data_time`、files/s、MiB/s |
| GPU | 利用率、显存使用、功率、各卡差异 |
| 主机 | CPU、内存、网络收发 |
| 算法 | loss、mAP、NDS、NaN、Checkpoint |

### 5.5 推荐判读口径

以下是经验性起点，不是所有模型的硬性 SLA：

| 现象 | 初步判断 |
| --- | --- |
| GPU 利用率 >80%，数据等待占比 <15% | 通常不是数据瓶颈 |
| 数据等待占比 >30% | 优先检查数据路径、DataLoader 和缓存 |
| 8→16 GPU 吞吐加速达到 1.7–2.0× | 多机扩展通常良好 |
| 节点或 GPU 利用率相差超过 10–15 个百分点 | 检查慢节点、数据分片或 rank 不均衡 |
| 单步一样、迭代数减半 | 每卡 Batch 固定时属于正常加速 |
| 单步变慢且网络持续高位 | 检查 NCCL 和跨节点通信 |

## 6. 用户自查顺序

当用户反馈“训练慢”时，按以下顺序提供信息：

1. 任务 ID；
2. 对照任务 ID；
3. 两个任务的 Worker/GPU 数和 `samples_per_gpu`；
4. 数据集和标注文件路径；
5. 两个任务是否使用同一源码、镜像和 Checkpoint；
6. 日志中的 `time`、`data_time`、每轮迭代数；
7. 平台 GPU 曲线的时间范围；
8. 希望比较的是单步时间、样本吞吐、epoch 时间还是收敛时间。

没有上述信息时，不应直接判断为“数据慢”或“Ray 多机无效”。

## 7. 平台侧排查顺序

平台管理员按以下顺序确认，不应先修改用户任务：

1. 查看任务是否排队以及实际开始时间；
2. 确认 Ray Worker 数、每 Worker GPU 数和节点分布；
3. 确认所有 rank 已启动，world size 符合预期；
4. 检查 NCCL、OOM、Pod 重启和异常退出；
5. 对齐日志中的单步耗时、`data_time` 和迭代数；
6. 查询任务时间范围内的 GPU、显存、功率、CPU、内存和网络；
7. 检查输入路径是否命中预期数据源和缓存策略；
8. 最后才做参数 A/B 或平台改动。

## 8. 当前案例的最终解释

这次单机与双机任务的核心关系如下：

```text
每卡 Batch 不变
        ↓
每张 GPU 的单步计算量不变
        ↓
单步时间仍约 3.6 秒
        ↓
GPU 数从 8 增加到 16，全局 Batch 从 64 增加到 128
        ↓
每轮迭代数从约 2649 减少到约 1325
        ↓
样本吞吐约提升 2.04 倍，epoch 耗时约减半
```

所以当前结论是：多机多卡链路工作正常，训练获得了接近两倍的吞吐提升；数据读取不是主要瓶颈。下一步应由算法团队明确采用“固定每卡 Batch”还是“固定全局 Batch”，再以同一数据与配置完成正式 A/B，并根据全局 Batch 调整学习率和 warmup。
