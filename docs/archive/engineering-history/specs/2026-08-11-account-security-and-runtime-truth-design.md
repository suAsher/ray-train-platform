# 本地账户安全与 Ray 运行态可信化设计

日期：2026-08-11
状态：待实现前评审
范围：测试环境与后续生产基线共用

## 1. 背景与目标

当前平台已经支持本地账号登录和管理员创建用户；但用户无法在 Portal 中自助修改密码，管理员无法禁用账号或安全地重置密码。同时，KubeRay 1.3 的 `Initializing`、`Suspended` 等运行态尚未完整映射到平台状态，容易在 UI 中显示为 `UNKNOWN`，降低任务状态可信度。

本次改造目标：

- 保留已存在的本地账号、密码哈希、租户和角色；不重置任何账号。
- 让本地用户可在 Portal 内修改自己的密码，完成后立即失效现有会话并重新登录。
- 让具备权限的管理员可创建、查看、禁用/启用同租户用户，以及重置用户密码；密码绝不在查询接口、日志或审计详情中返回。
- 完整映射当前 KubeRay RayJob 部署状态，让任务展示“排队中”“启动中”等可解释状态，而不是无意义的“未知”。
- 明确现有任务、日志、指标和产物的保留边界，避免 UI 把没有部署的可观测性能力表示为可用。

## 2. 非目标与安全边界

本次不做以下操作：

- 不删除、取消、重跑当前已经提交的 RayJob 或 RayCluster。
- 不自动安装 Loki、Prometheus、DCGM Exporter 或修改现有 ALB、VKE、TOS、Keycloak 配置。
- 不把 Kubernetes Secret、TOS 凭据、初始管理员密码或用户明文密码写入数据库、浏览器日志、API 响应或审计内容。
- 不改变 OIDC/Keycloak 登录路径；本地账户安全仅覆盖 `LOCAL_AUTH_ENABLED=true` 时的账号。

管理员不能跨租户操作普通租户用户；只有 SuperAdmin 可跨租户管理。任何管理员都不能通过普通管理入口修改其他 SuperAdmin 的账号。

## 3. 账户安全体验与权限

### 3.1 账户与安全页面

在当前用户菜单中新增“账户与安全”入口，仅本地登录用户可见。页面提供：

- 当前登录名与认证来源（本地 / Keycloak）只读展示。
- 当前密码、新密码、确认新密码三个字段；新密码长度和复杂度在前后端统一校验。
- 提交成功后显示一次性成功提示，清除浏览器认证状态并跳转登录页。
- Keycloak 用户展示“该账号由企业身份系统管理”，不出现本地改密表单。

后端沿用 `POST /api/v1/auth/password`，但改密完成后必须撤销该用户全部本地会话，而非只依赖浏览器删除 Token。

### 3.2 管理员用户管理

现有“配额与用户”页面保留创建与列表能力，增加每位用户的：

- 状态（启用 / 已禁用）。
- “重置密码”操作：管理员输入符合策略的新临时密码；提交后只返回成功状态，不回显密码。
- “禁用”与“启用”操作：禁用立即撤销全部本地会话，且被禁用用户不能登录或调用 API。

新增受控接口：

```text
POST /api/v1/local-users/{id}/reset-password
POST /api/v1/local-users/{id}/disable
POST /api/v1/local-users/{id}/enable
```

每个接口均执行：身份来源校验、调用者角色校验、租户边界校验、目标账号角色保护、输入 Schema 校验、审计记录和统一错误响应。

### 3.3 密码与会话实现

- 密码继续只保存强哈希；采用已有算法/参数时只进行兼容升级，不存储可逆数据。
- 新密码不能与当前密码相同，并设置明确的最小长度与复杂度规则；规则从配置读取而不是写死在前端。
- 为本地会话增加可撤销版本号或服务端会话记录。改密、管理员重置、禁用、角色/租户变更时递增版本或删除会话，使已签发 Token 失效。
- 登录中间件在每次本地认证时校验用户启用状态和会话版本。
- 审计仅记录操作者、目标用户、动作、时间、请求 ID 与结果；不记录密码或 Token。

## 4. Ray 运行态与调试工作区

### 4.1 训练任务状态映射

平台每 5 秒从 Kubernetes 重新观察任务；浏览器不应依赖人工刷新。

KubeRay 1.3 的状态需要映射为：

| KubeRay 状态 | 平台展示状态 | 用户说明 |
| --- | --- | --- |
| `Suspended` | `QUEUED` | 等待 Kueue/GPU 准入 |
| `Initializing` | `PROVISIONING` | 正在创建 RayCluster 与 Submitter |
| `Running` | `RUNNING` | 训练脚本正在运行 |
| `Complete` | `SUCCEEDED` | 任务已完成 |
| `Failed` | `FAILED` | 任务失败，显示原因与事件 |

当 `jobStatus` 为空时，平台状态原因优先使用 `jobDeploymentStatus` 和关联 Kubernetes Event。仅在 Kubernetes 对象确实无法读取或状态无法识别时显示 `UNKNOWN`。

RayJob Submitter Pod 模板必须始终包含 `restartPolicy: Never`。这个字段是 KubeRay 当前版本创建 Submitter Job 的必填项。已经以旧模板创建、缺少该字段的 RayJob 不进行原地篡改；需要由用户明确取消并按修复后的模板重新提交。

### 4.2 调试工作区

Dev Center 已经自动轮询工作区状态，因此不要求用户手动刷新浏览器。改造后额外显示“最后同步时间”和显式的“刷新状态”按钮，便于排障，但按钮不是状态更新的依赖。

当数据库记录为 `STOPPED` 且 Kubernetes 中不存在对应 RayCluster 时，UI 需明确展示“已停止”，而不是误导为正在启动。启动新工作区后应新建/替换记录并显示 `SUBMITTED` 或 `PROVISIONING`；若 GPU 被训练任务占满，则应显示资源等待原因。

## 5. 日志、指标、产物与保留策略

### 5.1 当前测试环境的事实

- Alloy 只能采集或转发日志，不能替代 Loki 的存储与查询；Loki 未部署时，Portal 无法查询已结束 Pod 的日志。
- Prometheus 与 DCGM Exporter 未部署或不可达时，GPU、节点和训练指标不会出现；这不是浏览器权限问题。
- 训练容器可以使用 TOS/NAS 写入 `checkpointUri`、`outputUri`，但平台目前不会自动扫描并生成完整产物目录；应把用户声明的 URI 与任务关联，并在后续增加受控的产物索引能力。

### 5.2 生命周期规则

当前 RayJob 模板的默认成功清理 TTL 是 600 秒：任务结束时 RayCluster 立即关闭以释放 GPU，RayJob CR 在终态后保留 10 分钟，数据库中的任务历史不会随 CR 删除。

修复项：模板必须分别传递并验证成功/失败 TTL；当前只使用成功 TTL 的行为不满足“失败任务更长保留”的产品语义。调试工作区目前没有实际执行的空闲回收控制器，后续应在控制器中落实 `idleTTLSeconds`，而不是只在数据库中保存配置。

上线 Loki 后，终态任务日志由 Loki 的 retention 控制；在 Pod 被删除后仍可查询。未上线 Loki 时，Pod 删除后日志不可恢复。

## 6. 验收标准

账户安全：

1. 已有本地账号可正常登录，改密后旧会话失效，新密码可登录。
2. TenantAdmin 只能管理本租户非特权账号；跨租户和特权账号操作均返回授权错误。
3. 禁用用户立即无法登录，已有会话无法继续访问；重新启用后可按有效密码登录。
4. 任何 API、数据库查询、浏览器网络响应与审计记录均不出现明文密码或 Token。

运行态：

1. KubeRay `Suspended`、`Initializing` 在 UI 分别显示为“排队中”“启动中”。
2. 新提交 RayJob 的 Submitter 模板含 `restartPolicy: Never`，KubeRay 能创建 Submitter Job。
3. Dev Center 在不刷新浏览器的情况下自动更新状态；停止的工作区不显示为启动中。
4. 任务详情清晰提示 Loki/Prometheus 未接入时的能力状态，不把空结果包装成“无日志/无指标”。
