# 训练平台自动同步功能仓：实施计划与接口梳理

2026-09-14；已按用户授权开始实现连接器及 OAuth2 委托边界，尚未发布；未上传业务权重、未变更数据库。以下新增字段、状态、接口能力均为建议合同，不能作为已上线接口使用。

## 1. 用户最终如何使用

目标：用户只需选择权重与目标功能仓；平台负责复制校验、上传、登记版本，并让两边都能追溯训练任务、MLflow Run、实验和数据来源。

本次完整验收目标是新训练任务自动同步。一键同步用于历史任务和联调，两者共用一套后台处理流程；只交付一键同步不能算完成本需求。自动模式由平台内部生成模型副本与版本，不要求用户训练结束后再手动登记、审批或点击同步。

**已有训练结果：**

1. 用户在「任务详情 → 训练产物」选择权重，登记为平台模型版本。
2. 平台完成副本复制及 SHA-256 校验，版本变为 `READY`。
3. 在「实验中心 → 模型 → 版本详情」点击「同步到功能仓」，选择团队、功能仓和模型类型，确认版本名与来源。
4. 页面显示排队、上传、校验、登记、完成或失败原因。完成后可跳转功能仓，查看同一权重与来源任务/Run。

**新训练任务：**

1. 提交任务时，在可选的「训练完成后同步到功能仓」区域配置目标和输出文件规则；默认不勾选。
2. 用户指定明确的输出相对路径，例如 `checkpoints/best.pth`。不默认递归同步整个输出目录，不根据文件名推断哪份权重最好。
3. 任务成功结束后，平台核对文件、生成不可变模型版本，待 `READY` 后自动启动同一同步流程。
4. 用户在任务详情和模型版本详情查看同步进度；上传失败可重试，不需要重新训练。

训练节点只写现有平台输出目录。向功能仓的传输由受控的后台 CPU 任务执行，不要求训练节点访问公网，也不向训练 Pod 注入功能仓凭据。

## 2. 功能仓与发布仓的关系

本轮补查了独立 Portal 的 `src/api/model/modalStore/publish.js`、`pubStore.vue` 和 `pubVersion.vue`。以下是页面及前端调用合同确认的关系，不代表发布仓后端已经生产写入验收。

| 系统 | 职责与当前可确认行为 | 本次范围 |
| --- | --- | --- |
| 训练平台 | 执行训练，记录 Job 与 MLflow Run，保存权重及来源 | 训练成功后自动同步指定产物 |
| 功能仓 | 保存模型类型和模型版本、文件；提供评估与模型转换入口 | 接收实际文件，创建版本，保存/查询/展示训练来源 |
| 发布仓 | 从已有模型版本选文件，组合为面向设备类型的发布版本 | 本次不自动创建发布版本，不改发布规则 |

发布版本创建调用 `POST /model/issueVersion/create`，前端提交 `issueWarehouseId`、`groupId`、`version`、`deviceType` 和 `modelFiles: [{modelVersionId, modelFileIds}]` 等字段。选文件时按 `convertFiles.deviceType` 匹配，缺少对应文件时提示先到功能仓发起模型转换。因此自动上传训练权重不等于已产生可发布的转换文件。

最终关系为：训练任务 → 功能仓模型版本 → 后续用户按既有评估/转换/发布流程选择该版本 → 发布仓版本。训练来源固定在功能仓模型版本上，发布仓可通过所引用的 `modelVersionId` 追溯；是否需要新增发布仓来源展示属于后续独立需求。

## 3. 已核对的真实能力及缺口

2026-09-14 浏览器访问了正式 Portal 功能仓详情。该页面存在模型版本列表、上传、查看、编辑、评估与转换入口。浏览器网络记录确认功能仓详情、版本分页和模型类型查询曾返回 200；出现过会话到期的 401，因此不能把浏览器登录作为稳定的后台认证。

以下接口名称来自独立 Portal 源码；上传/创建路径存在于前端调用中，不代表已用服务身份完成生产写入验收。

| 用途 | 现有前端调用 | 当前可确认范围 |
| --- | --- | --- |
| 选择功能仓 | `GET /model/functionWarehouse/page` | `groupId`、关键词、可见性、分页 |
| 功能仓详情 | `GET /model/functionWarehouse` | `functionWarehouseId` |
| 模型类型 | `GET /model/model/type/list` | `functionWarehouseId`、`groupId` |
| 上传文件 | `POST /system/api/file/minio/upload` | multipart 文件和 prefix |
| 分片上传/合并 | `POST /system/api/file/minio/chunk/upload`、`POST /system/api/file/minio/chunk/merge` | 已有分片、MD5、SHA-256 和合并调用；需后端确认服务身份适用性与会话隔离 |
| 创建模型版本 | `POST /model/model/version/create` | `functionWarehouseId`、`groupId`、`modelTypeId`、`version`、`description`、`production`、`paths` |
| 版本查询 | `GET /model/model/version/page` | 可分页查看；按来源/幂等键精确查询仍需确认 |

`paths` 中前端实际提交的文件字段是 `url`、`filename`、`fileSha256`、`fileSize`。已有路径转存接口 `/system/api/file/upload2minio`，但没有证据证明其后端能访问训练集群的 FSX 路径；不把它当作可直接使用的跨集群复制能力。

目前前端创建版本合同未见 `job_id/run_id/experiment_id` 或通用训练来源对象。已有 `mlflowViewUrl` 出现在评估报告/发布展示链路，不能直接覆盖成训练 Run 地址，混淆两种实验来源。

训练平台现有 `modellifecycle.Version` 包含 Job ID、可选 Run ID、模型版本 ID、文件长度与 SHA-256、代码/镜像及数据来源；当前不含 Experiment ID。同步前需要从已关联 Run 查询真实 Experiment ID，并固定到同步来源快照。

## 4. ID 与来源合同

三个 ID 不要求相等，也不能相互推算：

| 字段 | 意义与来源 |
| --- | --- |
| `jobId` | 平台训练任务 ID |
| `runId` | 产生这份权重的 MLflow Run ID，必须使用已核实的关联 |
| `experimentId` | 从该 Run 的信息读取其所属实验 ID，按字符串传输 |
| `trackingInstanceId` | 标识来源 MLflow 实例，避免跨环境 ID 混淆 |
| `platformModelVersionId` | 平台不可变模型版本，标识文件来源；同一版本允许主动同步多次 |
| `targetModelVersionId` | 功能仓创建后返回的模型版本 ID |
| `fileSha256`、`fileSize` | 双方校验后相同的权重内容身份 |

建议功能仓增加结构化 `trainingSource`，字段名由双方确认。示意载荷如下，不能直接调用线上接口：

```json
{
  "functionWarehouseId": "<目标功能仓ID>",
  "groupId": "<目标团队ID>",
  "modelTypeId": "<目标模型类型ID>",
  "version": "<用户确认的版本名>",
  "production": false,
  "paths": [{
    "url": "<功能仓上传接口返回的文件定位符>",
    "filename": "best.pth",
    "fileSha256": "<完整SHA256>",
    "fileSize": 123456
  }],
  "trainingSource": {
    "sourceType": "raytrain",
    "platformInstanceId": "<平台实例ID>",
    "platformModelVersionId": "<平台模型版本ID>",
    "jobId": "<平台JobID>",
    "trackingInstanceId": "<MLflow实例ID>",
    "runId": "<MLflowRunID>",
    "experimentId": "<真实ExperimentID>"
  }
}
```

可选携带代码摘要、提交号、镜像摘要、数据集及数据版本、manifest 摘要，并区分系统记录与用户补充。未知来源保留未知；不擅自补写历史 Run。业务数据样本不随权重同步。

一个 Job 可有多个 Run，续训也可能使用新的 Job/Run。导出必须对应产生所选文件的 Run；关联缺失或有歧义时显示「待确认训练来源」，不能选最近 Run 凑齐 ID。首批自动同步不生成缺少必要来源的“成功关联”版本。旧任务可由用户确认经过验证的来源后手动同步。

## 5. 功能仓后端需要确认的五组能力

尽量复用现有接口，不要求对方按建议路径重写。最低要求是下面的行为与返回值明确。

| 能力 | 请求/权限 | 必需返回与保证 |
| --- | --- | --- |
| 服务认证与目标权限 | 已验证可转发用户 OAuth2 access token；限定可写团队、功能仓；后台任务另需解决长时有效的用户委托或服务授权 | 用户请求转发方式已只读验证；仍需明确过期后的续期、后台授权及写权限。不能保存个人 Cookie充当后台认证，也不能假定 RayTrain PAT 可登录功能仓 |
| 可写目标查询 | 按当前授权查询团队、功能仓、模型类型 | 稳定 ID、名称和写权限；服务账号能写不等于任意平台用户能写 |
| 文件传输及校验 | 小文件或分片；上传会话绑定身份和目标；传入长度、摘要、幂等键 | 会话/文件 ID、已上传分片、过期时间、最终长度与 SHA-256；明确最大文件/分片大小、限流和清理机制 |
| 创建版本 | 已验证文件引用、版本信息、结构化训练来源；建议支持操作 ID | 目标版本 ID、页面 URL、持久化来源；允许相同 Job/Run 多次创建。若支持操作 ID，同操作重试返回原版本，新操作创建新版本；创建与来源落库应原子完成 |
| 精确查询及对账 | 按目标版本 ID 查询；建议支持操作 ID 查询 | 文件校验结果、来源字段、处理状态、错误原因。若不能按操作查询，创建响应丢失时转待确认，不自动再次创建 |

上传完成与版本登记是两项结果，后端需说明：版本创建失败时已上传文件如何复用、如何按上传会话过期清理。不能用“重新 POST 创建”处理所有超时，否则会产生重复版本和孤立文件。

## 6. 后台流程与失败恢复

```text
用户选择目标/配置自动同步
→ 确认任务终态、文件规则、管理权限、目标写权限与 Run 关联
→ 复用平台模型副本复制和 SHA-256 校验
→ READY 版本 + 固定训练来源 + 目标配置快照
→ 持久化同步记录
→ 后台上传/断点续传 → 目标校验 → 幂等登记版本 → 精确查询对账
→ 展示成功、目标链接与三个来源 ID
```

建议内部状态：`WAITING_SOURCE → QUEUED → UPLOADING → VERIFYING → REGISTERING → SUCCEEDED`；失败保留具体阶段。仅网络/限流/明确可重试服务端错误进入有上限的退避重试。认证、权限、摘要不符、目标删除、来源冲突需人工处理，不能无上限循环。

- 用数据库持久化记录和租约，复用平台后台 worker 模式；不用只存在内存里的 goroutine 保证可靠性。
- 用户每次主动发起同步都分配新的操作 ID，允许同一 Job、Run 或平台模型版本再次创建功能仓版本，且每次可以选择不同文件。不能把 Job ID、Run ID 或文件名当作全局去重键。
- 同一次操作的网络重试、提交期间的双击和后台恢复沿用操作 ID；请求摘要覆盖本次文件清单、摘要、目标、版本名及来源。只有操作重试去重，用户明确发起的新操作不去重。
- 创建请求超时先按操作 ID 对账；若对方尚无幂等及精确查询能力，则标记「登记结果待确认」，停止自动重发创建请求。用户核对目标后可明确发起新的同步，平台不把响应丢失伪装成失败后盲目重建。
- 只传已校验的不可变平台副本，不反复从仍在变化的个人输出路径上传。
- 自动模式仅在成功结束后执行。失败/取消任务保留的 checkpoint 可走用户明确选择的手动流程，并标明来源任务状态；不能自动当作成功训练成果。
- 一个明确文件规则对应一个候选文件；零个显示未找到，多个要求选择，避免静默“取最新”。首批不默认上传全部 epoch。
- 后台传输设置并发和带宽上限、有限缓冲，复用现有 CPU 工作节点；不占 GPU、不阻塞训练结束或状态协调。
- `production=false` 作为自动导入的建议默认值，需双方确认其业务含义。同步不会自动评估、转换、审批、发布或启动推理。
- 平台归档不自动删除功能仓版本。取消同步不回滚已完成的外部版本；已上传未登记文件按目标上传会话清理合同处理，不能删除用户既有文件。

## 7. UI 与可见性

保持现有一级菜单，在模型版本详情加「功能仓同步」区域；任务详情展示对应模型版本与同步结果。区域包含目标仓/模型/版本、当前阶段、进度、更新时间、失败原因、「重试」「查看功能仓」及来源跳转。

模型和同步元数据沿用平台共享可见规则；发起/修改同步由模型管理权限控制。目标功能仓的公开、私有、被邀请者权限仍由功能仓决定，不因源模型共享而扩大目标可见性。页面可显示目标名称及“需要目标仓权限”，不暴露可绕过权限的下载 URL。

普通使用说明新增/补充问题文章：「训练权重如何同步功能仓」「三个来源 ID 是什么」「自动同步失败如何重试」「续训产生的版本如何关联」。管理员凭据配置留在运维文档，不塞进用户接入步骤。

## 8. 分三批实施

| 批次 | 交付 | 完成门槛 |
| --- | --- | --- |
| 一：接口合同与测试目标 | 确认上述五组能力、团队映射、测试功能仓、认证和来源字段 | 用户委托可读可写；来源可持久化读回；大文件协议和校验明确，登记响应丢失有明确处置 |
| 二：已有模型一键同步 | 后台任务、数据库记录、Portal 状态/按钮、用户帮助 | 专用模型完整上传和来源跳转；超时重试/权限拒绝/摘要错误/重启恢复可验证；同操作不意外重复，新操作可再次创建 |
| 三：训练完成自动同步 | Web/CLI 可选配置、文件规则、成功终态触发与持久恢复 | 一次配置后自动走通；失败任务不误传、缺来源不造假、重复事件只导入一次、其他训练不受影响 |

数据库迁移编号、组件构建范围、发布版本须在开始实现时重新核对，不能根据本计划固定。预计涉及后端及数据库、独立 Portal `dev`；若开放 CLI 配置则同时更新 `spk-rayjob` 下载组件。不改用户训练代码、不把代码放入训练镜像。

开发仍按候选先送构建机验证、通过后同步四端、只构建变更组件的流程。需要迁移时先完成该次获准的备份与隔离恢复验证；本轮计划不授权生产数据导出或业务权重验收。

## 9. 最低验收清单

1. 专用小权重和代表性大文件传输成功，源/目标字节数及 SHA-256 相同。
2. 功能仓读回完整 Job/Run/Experiment 及平台版本来源，页面链接打开对应对象；评估 Run 地址不被训练 Run 覆盖。
3. 同操作的重复提交、重复事件和进程重启不意外产生重复版本；用户主动创建新操作可再次同步同一 Job/Run，并可选择不同文件。登记响应丢失时先对账或提示待确认，不盲目重发；不同内容复用同一操作 ID 被拒绝。
4. 源模型无管理权限、目标无写权限、凭据失效、目标被删除均明确失败；不越权上传。
5. 没有 Run、Run 关联歧义、缺文件、多文件、仍在写入、摘要不符均不能显示同步成功。
6. 自动同步关闭时行为不变；旧 Web/CLI 请求无新增必填字段；历史数据不自动补传。
7. 开关关闭可停止接受新同步；已有记录可审计、可恢复，关闭功能不删除模型或功能仓版本。
8. 发布前后核对运行任务的 RayJob/RayCluster/Pod UID、状态和重启数；训练与 MLflow 继续工作。

## 11. OAuth2 用户令牌只读联调结果

用户提供的机制：将可信 oauth2-proxy 转发的 `X-Auth-Request-Access-Token` 作为功能仓请求的 `Authorization: Bearer <token>`。

2026-09-14 已在已登录 Portal 浏览器中验证，调用 `/oauth2/auth` 获取同名响应头，令牌仅在函数内存中使用，没有输出令牌、写文件或持久保存。每次模型查询使用 `credentials: omit`，排除依赖浏览器 Cookie 的误判，并禁止自动跟随重定向。

| 验证 | 结果 |
| --- | --- |
| 正式 Portal `/oauth2/auth` | HTTP 202，返回 access-token 头 |
| 正式功能仓模型类型查询，无 Cookie、无 Bearer | HTTP 401 |
| 同一查询，只携带 OAuth2 Bearer | HTTP 200，业务 code=0，返回 2 个模型类型 |
| 功能仓详情，只携带 Bearer | HTTP 200，业务 code=0，包含 permissionCodes 等字段 |
