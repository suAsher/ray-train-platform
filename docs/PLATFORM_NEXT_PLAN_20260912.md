# RayTrain 下一步平台计划

本计划按用户收益和依赖安排建议批次，不给未经评估的工期承诺，也不授权创建凭据、提交评估、发布模型、启动服务或改变调度。每批先形成可审阅变更与验收目标，再按当次明确授权执行。

## 起点：2026-09-12 已完成

完整共享 MLflow 程序入口已上线，普通使用说明已汇总为 7 个主题，历史自定义内容完整保留。后端 `6fbd2b09`、`release-20260912-07-6fbd2b09`、Helm 218、schema 48；Portal dev `610298a4`、CI 33859、Helm 1044 的新总览、API 指南与帮助页已在浏览器确认。Portal Pod imageID 仍因 Kubernetes 管理 API 超时未核对，不能以 CI 或页面证据替代。

本轮实际交付四项：

1. 原生 SDK / REST Tracking URI：`https://raytrain.wellspiking.ai/api/v1/mlflow-native`。
2. 显式个人 PAT scope：`mlflow:full`，旧令牌不自动升级；撤销后立即失效。
3. 与现有 MLflow 网页一致的共享范围：实验、Run、Metric、Param、Tag、Artifact、删除和 Model Registry 操作均使用原生 MLflow ID，不按平台用户或训练 Job 过滤。
4. Portal 普通用户入口：实验中心以共享 MLflow 总览和 API 指南为主，独立实验和受限集成能力保留为高级能力。

生产验收覆盖全部原有实验分页、专用 Run 参数/指标历史、文件上传下载 SHA-256、结束时间和令牌即时撤销；隔离 MLflow 3.14 SDK 验收覆盖模型版本与 alias 操作。现有 5 个活跃训练任务及其集群、Pod 的 UID/状态/重启数未变。证据见[验收记录](MLFLOW_NATIVE_HELP_VALIDATION_20260912.md)。

独立实验 REST、六方法 SDK、集成身份、实验级 grant 与受控产物接口仍兼容，生产验收见[集成能力验收](MLFLOW_INTEGRATIONS_VALIDATION_20260912.md)。这些受限接口用于需要限定资源边界的系统对接，不是标准 MLflow 接入的前置步骤。

当前仍未完成的是模型生命周期闭环、调度能力真实启用、IDC 连接器试点以及平台/MLflow 数据库可恢复演练。下面的计划只描述下一批建议，不代表已经获得训练、评估、审批、服务启动、数据源接入、调度切换或凭据签发授权。

## 并行基础设施计划

### 团队节点、TAS、抢占

最近已知状态是团队专属节点绑定尚未落地，TAS 与闲时抢占关闭；实施前必须重查实际配置。建议分三批，任一批不通过就不启用下一批：

1. **先落实团队/卡型与节点池边界。** 明确物理池、配额、共享或独占规则，建立一致的标签、选择器和队列策略，验证跨团队不能误用、卡型不能混入同一 WorkerGroup，以及容量不足时的排队原因。节点绑定不能代替配额，不自行修改 `local` 的 24 卡配额。
2. **再统一启用 TAS。** 同时校验 Topology、ResourceFlavor、队列和任务 PodSet 意图，先 server-side diff，再在安全窗口用获准的小任务与多 Worker 任务验证布局和碎片效果；避免只开后端开关的半配置。按 release 流程核对 admitted/running 工作负载与切换前提，不重启或删除现有训练。
3. **最后做闲时借用与抢占恢复。** 先证明 checkpoint 可恢复，再用专用正常/闲时任务验证额度回收、恢复步数、数据一致性和失败退出。当前单 Worker、单 GPU 的闲时契约不能直接推广成任意任务抢占。抢占会主动影响任务，需单独批准精确测试对象、队列变化与窗口。

用户收益分别是团队资源边界清晰、多机布局可解释、空闲资源可以受控利用；不能仅凭“总空闲 GPU 足够”承诺立即运行或宣称碎片已解决。

### IDC 小目录试点

IDC 同步开关已启用但此前没有连接器和同步记录。先由管理员确认一个受控只读目录、目标前缀、数据负责人、容量与网络窗口，再登记连接器并执行获准的小目录同步。

验收新增、修改、重复同步、源端删除 tombstone、失败重试、对象数量/容量和 inventory 摘要；再从成功运行发布 `READY` 数据版本，核对训练可读内容和可追溯来源。源目录不改写，源删除不映射为对象或已发布版本删除。试点通过后再决定全量与定时，不能因为开关已开就声称 labeled 正在自动同步。

### 数据库恢复与高可用

平台 PostgreSQL、MLflow PostgreSQL 与产物存储都需要持续可验证的恢复路径。下一批先盘点备份位置、保留策略、恢复时间目标、可接受数据损失和演练窗口，再做隔离恢复演练。

恢复验收应核对租户/用户归属、Job 与 Run 关联、实验记录、Artifact 摘要、Registry 记录和审计链路。已有一次 schema 恢复证据不等于持续保障；平台/MLflow 数据库单实例问题仍需后续高可用方案。真实切换与数据恢复需要单独维护授权。

## 每批如何交付与销项

每批保留一份简短记录：具体用户路径、范围与前提、候选提交、构建机验证、线上配置与镜像、获准身份的真实结果、未完成项。先在构建机验证候选，再同步四端；Portal 使用独立 `dev` 和自身 CI/CD。只构建变更组件，代码不进训练镜像。

涉及迁移先验证旧数据兼容和可恢复备份；涉及控制面发布，前后比较活跃 RayJob / RayCluster / Pod 的 UID、状态和重启数。个人数据归属不随本计划迁移或删除。具体发布、凭据签发、数据源接入、训练/评估提交、调度切换与服务启动的授权分别记录，不把历史设计或本计划当作执行许可。
