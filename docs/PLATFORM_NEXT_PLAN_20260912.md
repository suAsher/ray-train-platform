# RayTrain 下一步平台计划

本计划按用户收益和依赖安排建议批次，不给未经评估的工期承诺，也不授权创建凭据、提交评估、发布模型、启动服务或改变调度。每批先形成可审阅变更与验收目标，再按当次明确授权执行。

## 起点：已能做什么，还缺什么

**用户 2026-09-12 的最新优先级：完整共享 MLflow 接入、普通用户帮助分类汇总。** 原生网页一直是共享空间；机器接入也应优先提供原生 SDK 全量查询和读写。独立实验/实验级授权是可选能力，不是所有调用方必须使用的主流程。新增 `/api/v1/mlflow-native` 与 `mlflow:full` 的当前发布状态以本次验收记录为准，不能从代码存在推定上线。

阶段 B 已发布独立实验 REST 创建、分页、读写、结束 Run，以及固定 MLflow 3.14.0 的六项 SDK 方法；这一可选子集使用 REST 预创建的**平台 Run ID**。已有训练继续使用 Job 与上游 Run 的可信关联。独立集成身份、实验级 grant 与受控 Run 产物已发布至 `release-20260912-05-80dd1642`、Helm 216、schema 48，生产文件读写、授权与撤销以及 SDK 结束时间均已验收，详见[验收记录](MLFLOW_INTEGRATIONS_VALIDATION_20260912.md)。这些受限接口的旧 PAT 合同保持兼容。

当前查询是有界视图，不是完整历史导出；创建异常通过同键请求对账，没有后台自动恢复 worker。本轮产物提供分片上传、续传、SHA256 完整校验、不可变 READY 和受控下载；这尚不是不可变模型候选、独立评估、审批和 Serving 的平台闭环。原生 MLflow 管理界面仍是共享入口，不能当作资源隔离或审批有效的证据。

依据：[阶段 B 发布与验收](MLFLOW_EXTERNAL_TRACKING_VALIDATION_20260912.md)、[现状快照](CURRENT_STATE_20260911.md)、[生命周期设计](superpowers/specs/2026-09-12-mlflow-lifecycle-design.md)。快照与设计中的历史状态不能代替实施前重查。本轮继续补做的浏览器验收、SDK 读回修订和使用说明整理，应以对应提交、线上版本与新验收证据销项；不得提前算作全部通过。

| P0-2 集成身份与资源 grant | 外部系统只获得指定实验/模型的能力，不共享个人或管理员 PAT | 先确定资源粒度、授权人、凭据寿命、机器身份与团队成员关系；旧 PAT 不自动增加权限 | 新建集成身份独立审计；实际权限为 scope、有效团队与资源 grant 的交集。验证未授权资源、撤销、过期、跨团队和分页游标均不能恢复访问；旧 Job/Run 与 CLI 行为不变。首批真实身份和 grant 的创建需明确目标授权 |
| P0-3 恢复能力与运行手册 | 故障后有可验证的数据恢复路径，发布不靠“已有备份文件”判断安全 | 盘点平台 PostgreSQL、MLflow PostgreSQL 与产物存储，确定业务可接受的数据损失和恢复时间目标 | 分别完成受限备份、保留策略、失败告警及隔离恢复演练；恢复后核对归属、Run 关联、模型文件摘要和必要记录。已有 schema 45 单次恢复证据不等于持续保障；平台/MLflow 数据库单实例问题仍需后续高可用方案。真实切换与数据恢复需单独维护授权 |

P0-1 于 2026-09-12 已完成 guofeng.su / local 专用生产外部实验的 REST / SDK 读写、幂等、真实元数据读回、只读与终态拒写，以及两枚短期 PAT 撤销后 401；登录 Portal 的帮助、配额、训练 Run 对比和关联、外部实验、调试票据与真实错误提示均补验。证据见[使用说明与 SDK 补验记录](HELP_SDK_ACCEPTANCE_20260912.md)。剩余为目标 infer 集群 Pod imageID、第二合法身份的隔离验收及实际对接方身份/网络交付；不能提前关闭整个 P0-1。

P0-2 已交付所有者绑定的独立身份、1–30 天令牌、实验级实时 grant 和单凭据/授权/身份撤销。生产已完成两枚独立机器身份之间的无 grant/授权/撤销验证，三枚测试令牌撤销后均 401；不同实际人类用户/团队验收仍需按实际对接目标落实。管理上限为 20 个身份（含撤销）、每身份 20 枚未撤销令牌和 100 个 grant（含撤销历史）。未提供单 Run grant；这不是完整共享 MLflow 接入的前置条件。

本轮发布通过后，下一批优先是**不可变模型候选 → 固定输入的独立评估**，再进入审批与服务。实际对接方的身份、允许实验、负责人和网络验收仍需明确，不通过扩大个人 PAT 权限代替。

| P1-3 Registry 版本与审批 | 用户能看到哪个模型版本经过什么评估、由谁批准，以及当前发布版本 | P1-2；明确审批者、目标模型名、发布目标和别名规则；先解决原生 UI / API 绕过审批的写路径 | 申请人不能自批生产发布；审批绑定不可变候选、报告与策略，任一变化失效。重复发布不产生重复版本，不确定结果先对账；并发别名提升需版本检查。能回到已验证旧版本并保留审计。未封住原生旁路前不得声称“审批强制生效” |

这一阶段放在现有「实验中心」的模型、评估和发布子页中，保持 11 个一级菜单职责清晰。每个按钮须具备实际状态、权限、失败原因和完成证据；文件上传成功、评估通过、Registry 登记成功是三个不同结果。

P1-1 的受控文件底座已上线验收：独立 Run、20 GiB 单文件、8 MiB 固定分片、100 GiB 所有者逻辑预算、16 个待完成上传、24 小时有效期及 15 分钟校验上限；生产完成 8,388,641 字节两片上传与下载 SHA256 核对。下一批模型候选应按用户实际需求选择原生 MLflow 模型版本或获准 READY 产物，固定来源 Run、代码/数据/运行时版本；控制面不加载或执行模型。P1-2 随后固定候选与数据版本，独立记录评估状态、资源使用和报告；本轮不创建评估训练、不启用模型审批或推理服务。

## 与模型链路并行推进的基础设施

### 团队节点、TAS、抢占必须按依赖逐步验收

最近已知状态是团队专属节点绑定尚未落地，TAS 与闲时抢占关闭；实施前重查实际配置。建议分三批，任一批不通过就不启用下一批：

1. **先落实团队/卡型与节点池边界。** 明确物理池、配额、共享或独占规则，建立一致的标签、选择器和队列策略，验证跨团队不能误用、卡型不能混入同一 WorkerGroup，以及容量不足时的排队原因。节点绑定不能代替配额，不自行修改 `local` 的 24 卡配额。
2. **再统一启用 TAS。** 同时校验 Topology、ResourceFlavor、队列和任务 PodSet 意图，先 server-side diff，再在安全窗口用获准的小任务与多 Worker 任务验证布局和碎片效果；避免只开后端开关的半配置。按 release 流程核对 admitted/running 工作负载与切换前提，不重启或删除现有训练。
3. **最后做闲时借用与抢占恢复。** 先证明 checkpoint 可恢复，再用专用正常/闲时任务验证额度回收、恢复步数、数据一致性和失败退出。当前单 Worker、单 GPU 的闲时契约不能直接推广成任意任务抢占。抢占会主动影响任务，需单独批准精确测试对象、队列变化与窗口。

用户收益分别是团队资源边界清晰、多机布局可解释、空闲资源可以受控利用；不能仅凭“总空闲 GPU 足够”承诺立即运行或宣称碎片已解决。

### IDC 连接器先做小目录试点

IDC 同步开关已启用但此前没有连接器和同步记录。先由管理员确认一个受控只读目录、目标前缀、数据负责人、容量与网络窗口，再登记连接器并执行获准的小目录同步。

验收新增、修改、重复同步、源端删除 tombstone、失败重试、对象数量/容量和 inventory 摘要；再从成功运行发布 `READY` 数据版本，核对训练可读内容和可追溯来源。源目录不改写，源删除不映射为对象或已发布版本删除。试点通过后再决定全量与定时，不能因为开关已开就声称 labeled 正在自动同步。

## 每批如何交付与销项

每批保留一份简短记录：具体用户路径、范围与前提、候选提交、构建机验证、线上配置与镜像、获准身份的真实结果、未完成项。先在构建机验证候选，再同步四端；Portal 使用独立 `dev` 和自身 CI/CD。只构建变更组件，代码不进训练镜像。

涉及迁移先验证旧数据兼容和可恢复备份；涉及控制面发布，前后比较活跃 RayJob / RayCluster / Pod 的 UID、状态和重启数。个人数据归属不随本计划迁移或删除。具体发布、凭据签发、数据源接入、训练/评估提交、调度切换与服务启动的授权分别记录，不把历史设计或本计划当作执行许可。
