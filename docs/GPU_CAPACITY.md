# GPU 额度、容量与排队提示

本文描述候选功能的使用方式；是否已经上线，须以发布记录和当前页面验收为准。

## 如何理解页面数字

| 指标 | 含义 |
| --- | --- |
| 团队剩余额度 | 团队允许继续申请的 GPU 数量，不代表集群现在有这些空闲卡 |
| 资源池已分配 | 符合当前团队节点规则的节点上，非终态 Pod 已申请的 GPU，包含调试环境 |
| 已预留未落地 | Kueue 已分配到节点、尚未由 Pod 占用的资源；与 Pod 去重后计算 |
| 资源池空闲 | 节点可分配 GPU 扣除上述占用后的数量，不是 GPU 利用率或显存余量 |
| 可容纳 worker / 节点 | 按提交表单中的每 worker GPU、CPU、内存估算，可容纳的 worker 数及所在节点数 |

例如，团队剩余额度 24 卡、资源池空闲 0 卡时，仍可提交，但任务需要等待实际资源释放。即使总计空闲 8 卡，如果分别散落在四台节点、每台仅空闲 2 卡，也无法放置一个申请 8 卡的 worker；四个各申请 2 卡的 worker 则可能满足 GPU 条件，还需要检查 CPU、内存及准入规则。

提交页、任务详情、调试环境与资源页面显示容量参考。任务详情和 `spk-rayjob diagnose <job-id>` 使用后端同一套容量解释。任务自己的额度占用会从详情的比较基数中排除，避免把当前任务误判为超额。

## 等待原因

- 团队额度不足：申请超过团队剩余额度。
- 空闲 GPU 不足：额度允许，但资源池没有足够空闲卡。
- GPU 碎片：总空闲卡数足够，但单个 worker 无法放入现有节点。
- CPU 或内存不足：GPU 条件满足，其他资源不满足。
- 没有符合条件的节点：节点状态、资源类型、维护标记或团队节点规则限制。
- 已准入、正在启动：不能因为后来空闲卡减少，就把当前启动状态解释为排队缺卡；镜像拉取、挂载等失败仍以对应状态和日志为准。
- 容量暂不可用：观察失败或预留信息无法可靠解释，不显示虚构的零空闲。

这些数字是带时间戳的快照，不承诺立即启动。集群准入、公平性和并发提交可能在快照之后改变结果。页面定期刷新；后端对同资源池的原始观察共享短期缓存，团队额度、权限、节点规则和申请规格仍单独计算。

## 减少碎片的行为边界

新建训练和调试 worker 优先使用已有占用且能容纳当前规格的节点，同等条件再考虑团队集中。它是调度偏好，保留 Kueue 准入和节点硬约束，不能保证碎片永远为零。

此调整不搬迁或重启既有任务。已有任务产生的碎片通常需要等待任务自然结束；容量查询失败时新建任务继续按原有硬约束调度，不以观察故障阻断提交。

## 接口与权限

- `GET /api/v1/capacity`：查询当前身份所属团队的资源池、额度与申请规格容量；PAT 需要 `jobs:read`。
- `GET /api/v1/jobs/:id/scheduling-capacity`：查询有权访问的任务在提交、排队、准入和启动阶段的容量参考；不读取训练日志。
- 普通成员不返回节点清单、其他团队任务或用户身份；管理员节点视图只包含容量聚合信息。
- 查询只读，不进行资源预留、不修改配额，也不会启动任务。
