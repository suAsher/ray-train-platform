# Platform HTTP telemetry

Candidate configuration; deployment and live backend acceptance are separate release gates. The historical `observability_canary` database, credentials and OTLP ports remain independent.

## Data contract

The gateway accepts only the backend client URI `spiffe://observability.raytrain.local/ray-train-platform/backend-telemetry` on TLS port **14318**. Only `POST /v1/traces` and `POST /v1/logs` are routed. Both Envoy and Collector bound a request to 1 MiB; exporter batches contain at most 512 records. Native OTLP, metrics and health listen on loopback. NetworkPolicy is defense in depth only, pending actual CNI enforcement.

The source must identify as `service.name=ray-train-backend`. HTTP method is an enum, route is at most 256 characters and must be the backend's registered template or `unmatched`, and HTTP status is an integer in 100–599. Logs additionally carry integer `duration_ms` in 0–86400000. Body must be exactly `http.request.completed`; unexpected bodies are dropped. Trace/span IDs retain the bounded OTLP ID types. No request IDs supplied by users are retained.

The collector removes unknown resource/span/log/scope attributes, scope name/version, resource/scope schema URLs, span status messages, trace state, all span events and links. Span name is rebuilt from the accepted method and route. Log severity and event name are fixed. Five resource attributes are set centrally, including `raytrain.telemetry.source=production`. This first pipeline accepts HTTP request completion only; it does not ingest application error text, full application logs, user training logs, request headers, bodies, query strings or SQL parameters.

The authenticated backend must supply registered route templates; the gateway cannot independently discover the backend's router. Its character/length validation is a second boundary, not proof that a route string was registered. Application tests must verify the template source.

## Storage and permissions

`schema.sql` creates three ReplicatedMergeTree local tables, a trace lookup materialized view, and three Distributed query tables in `raytrain_observability`. Trace and lookup retention is **30 days**; log retention is **7 days**. TTL is asynchronous and partition based; this is not an immediate deletion guarantee. Retention changes require a reviewed additive schema change and recording the new TTL policy; do not edit or drop historical canary tables.

| SQL identity | Exact grants |
| --- | --- |
| `platform_otel_ingest` | INSERT, SHOW COLUMNS on production `otel_logs`, `otel_traces` |
| `grafana_platform_query` | SELECT on production `otel_logs_all`, `otel_traces_all`, `otel_traces_trace_id_ts_all` |
| `platform_distributed_reader` | SELECT on the three production local tables, internal only |

The existing `telemetry` cluster secret propagates the initiating SQL user to replicas. Reusing that cluster for Grafana would require granting Grafana the local tables too. The separate `telemetry_platform_query` cluster instead authenticates remote reads with `platform_distributed_reader` using a Secret available only to ClickHouse. It has **no cluster secret**. The Grafana profile fixes `prefer_localhost_replica=0` so ClickHouse cannot shortcut the remote reader and demand local-table access from the initiating Grafana user. The existing cluster secret remains unchanged for replication and ON CLUSTER DDL. Both internal reads and Grafana use mTLS native port 9440; the Grafana URI is not authorized for admin HTTP port 8443. Grafana cannot perform INSERT, DDL, arbitrary remote table functions or SELECT on local tables or sensitive system tables.

The query account has `readonly=1`, two threads, 1 GiB query memory and 30-second query timeout. The official Grafana driver sets `max_execution_time` on every query, so only this setting is `changeable_in_readonly`, bounded to 1–30 seconds. All other setting changes remain forbidden. Datasource configuration and fixed table names avoid requiring broad introspection grants. Grafana folders are not tenant authorization: this datasource is for platform operators only.

## Required Secret references

No credential values or Secret objects are generated by this directory.

| Namespace / Secret | Keys / consumer |
| --- | --- |
| `clickhouse/clickhouse-auth` | `platform-ingest-password-sha256`, `platform-query-password-sha256`, `platform-distributed-password-sha256` for the three SQL users |
| `opentelemetry/otel-platform-clickhouse-auth` | `password` matching the ingest hash |
| `grafana/grafana-clickhouse-auth` | `password` matching the Grafana query hash |
| `clickhouse/clickhouse-platform-distributed-auth` | `password` matching the internal reader hash; mounted via environment only in CH |

The gateway continues to use its own `obs-mtls-otel-gateway` client certificate for export. Backend and Grafana use their own dedicated leaves. CA private keys are never mounted in runtime pods.

## Release sequence and rollback

After the release owner's authorization, provision the referenced credentials, apply the reviewed ClickHouse user/remote-cluster and proxy configuration, and roll the two CH replicas one at a time. The new remote password environment variable and static Envoy identity allowlist require a controlled Pod rollout; user XML hot reload alone is insufficient. Verify existing replication/canary continuity before proceeding. Run the separate bootstrap Job only after both replicas are Ready; it requires the existing schema-admin client ConfigMap and certificate. The production bootstrap has its own Job and ConfigMap names.

Apply the gateway's reviewed configuration and rollout with retained queue PVCs; do not delete pending queues. Then enable the backend emitter and Grafana datasource. Monitor queue failures, dropped records, export failures, insertion latency and replication lag. Rollback disables backend export first; keep production tables, queue PVCs and SQL secrets while draining. Do not delete historical storage or roll back database schemas through Helm.

## Builder gates

`python3 -m unittest discover -s ops/observability/next/tests -p test_platform_pipeline.py -v` pins the static ingress, privacy, SQL and retention contracts. The release harness runs the exact pinned Collector/Envoy/ClickHouse images on a private Docker network with synthetic certificates and random ephemeral SQL credentials:

```sh
python3 ops/observability/next/clickhouse/verify-runtime.py \
  --phase platform --output /tmp/rtp-platform-runtime-<unique>
```

Run `--phase full` for the historical canary and production acceptance together. The separate `otel/verify_protocol_recovery.py --output <unique>` additionally exercises canary gRPC Export and crash recovery with the production pipeline present. Test code does not contact Kubernetes, production endpoints or production Secrets. It verifies binary OTLP HTTP export matching the backend protocol, mTLS rejects anonymous/wrong roles, allowed methods/paths, oversized request rejection, actual sensitive field removal, cross-replica ingestion, Distributed SELECT with no Grafana base-table grants, unexpected Body/route rejection and denied writes/system reads. Private test directories contain synthetic key material and redacted result files; remove them after retaining the public result evidence.
